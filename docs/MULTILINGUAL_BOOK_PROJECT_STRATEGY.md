# Multilingual Book Project Strategy

## Purpose

This document records the future architecture direction for multilingual Book Projects in Interleaf Reader.

It is a product and architecture strategy, not an M2 implementation plan. M2 remains focused on the local-first English Study Mode reading loop and vocabulary support. Real translation storage, translation generation, alignment tooling, provider integration, and Mixed Mode rendering remain future work.

## Product Concept

A **Book Project** is the future container for one source book and its related language versions.

In the current app, the practical unit is a locally imported EPUB used for English reading. In the future architecture, that same user-facing book can grow into a Book Project that may include:

- the original source version
- one or more translation versions
- user-provided translations
- AI-generated translations
- alignment metadata between versions
- future Mixed Mode rendering data

The Book Project should remain local-first unless a separate cloud/sync decision is made later. Adding multilingual support must not imply public sharing, upload flows, remote libraries, or provider calls in the MVP.

## Add Translation Version

Future Book Projects should support an **Add translation version** workflow.

At a product level, this means the user can attach another language version to the same Book Project instead of importing it as an unrelated book. The translation version may be complete, partial, rough, edited, or regenerated over time.

The workflow should eventually answer:

- Which source book does this translation belong to?
- What language is this version?
- Was it provided by the user or generated by AI?
- Does it align by chapter only, or by deeper units?
- Can the user edit, replace, remove, or regenerate it?

This document does not define the final storage schema or UI. It only records the direction that translations should belong to a Book Project rather than being treated as disconnected books.

## Translation Sources

### User-Provided Translation

A user-provided translation is a translation the user imports or pastes from a source they are allowed to use.

Future handling should treat it as user-owned local content. The app should avoid assuming it is public, shareable, or generated by the app. Metadata should record that the translation was user-provided so the app can distinguish it from AI output.

User-provided translation is important because many readers may already have:

- a purchased bilingual edition
- their own translation notes
- a public-domain translation
- a manually prepared translation file
- a translation produced outside Interleaf Reader

### AI-Generated Translation

An AI-generated translation is produced by a provider or local model through a future translation boundary.

AI-generated translation should be clearly labeled as generated output. The app should preserve provider-agnostic architecture and should not assume DeepL, OpenAI, Google, or any single vendor is the only path.

Future decisions are still required for:

- provider boundary and credentials
- privacy and data-flow disclosure
- cost and quota behavior
- local vs remote generation
- retry/regeneration semantics
- user editing and provenance

No AI translation provider is implemented for M2.

## Mixed Mode Variants

Future multilingual architecture needs to distinguish two related but different Mixed Mode concepts.

### Generated Mixed

**Generated Mixed** means the app creates a mixed-language reading version from one source text plus generated translations.

Example future behavior: the app starts from an English chapter, translates selected spans into Chinese, and renders an interleaved English-Chinese reading experience.

Generated Mixed depends on future translation generation and alignment. It should be treated as derived data, not as the canonical translation.

### Paired-Version Mixed

**Paired-version Mixed** means the app combines two existing versions already attached to the same Book Project: usually the source version plus a user-provided or previously generated translation version.

Example future behavior: the app aligns chapter 3 of the English EPUB with chapter 3 of a Chinese translation, then renders a mixed reading view using both versions.

Paired-version Mixed depends on version pairing and alignment quality. It may work even when the app did not generate the translation itself.

## Alignment Strategy

Alignment should start coarse and become more precise over time.

### Phase 1: Chapter Alignment First

The first viable architecture should align translation versions at the chapter level.

Chapter alignment is the right first step because:

- EPUB structures often already expose chapters or spine items.
- It supports simple paired reading and future side-by-side navigation.
- It is easier to inspect, correct, and recover when mismatches happen.
- It avoids pretending that paragraph or sentence alignment is reliable before the app has tooling for it.

Chapter alignment can support early future features such as selecting a translated chapter, showing paired chapters, and preserving progress within a Book Project.

### Later: Paragraph, Sentence, and Word Alignment

Paragraph, sentence, and word alignment should be deferred until after chapter-level architecture is stable.

Deeper alignment is valuable for:

- precise Mixed Mode rendering
- hover or tap translation mapping
- bilingual sentence comparison
- vocabulary-aware translation display
- future reading assistance features

However, deeper alignment is also more fragile. It has to handle OCR noise, missing paragraphs, split or merged sentences, translator omissions, punctuation differences, reflowed EPUB HTML, and language-specific segmentation.

For that reason, deeper alignment should be future architecture work, not an M2 requirement.

## Why This Is Future Architecture

This strategy is intentionally not an M2 implementation.

M2 should not add:

- translation storage
- translation import workflows
- translation provider calls
- AI translation generation
- Mixed Mode rendering logic
- paragraph, sentence, or word alignment
- new cloud, account, or sync behavior
- broad PRD restructuring

The value of this document is to prevent future multilingual work from being designed as isolated features. Book Project, Add translation version, translation provenance, Mixed variants, and staged alignment should fit together as one architecture when the project reaches the translation milestones.

## Open Decisions

- Final Book Project data model
- Translation version metadata fields
- Import formats for user-provided translations
- Provider boundary for AI-generated translations
- Secure handling of provider credentials
- Local-only vs optional companion-service translation
- Editing and regeneration behavior
- Alignment review and repair UX
- Migration path from current single-book records to future Book Projects
